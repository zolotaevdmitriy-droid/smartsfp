# Engineering journal

Один файл на одну рабочую сессию, имя `YYYY-MM-DD-<тема>.md`. В файле — то,
что реально делали: команды, вывод (или сокращённый), наблюдения, решения,
блокеры. Не «как должно быть», а «как было».

Из этих файлов в любой момент можно собрать отчёт по итерации, по фазе или
для УзГИС-аудитора — материал хранится с разрешением «команда + ответ модуля
+ интерпретация», что и нужно для технической документации.

## Структура одной записи

```markdown
# YYYY-MM-DD — <короткое название>

**Участники:** ...
**Цель:** одной строкой
**Итог:** одной строкой (заполняем в конце)

## Контекст

Что было известно к началу сессии (1-2 абзаца).

## Шаг N — <название>

**Команда:**
    <код или shell>

**Вывод (фрагмент):**
    <ключевые строки, не весь simian-роман>

**Наблюдение:** что увидели.
**Решение:** что из этого следует.

## Итоги сессии

* Подтверждено: ...
* Опровергнуто: ...
* Заблокировано: ... (с указанием, кто отвечает за разблокирование)
* Дальше: ...
```

## Конвенции

* **Сокращайте вывод.** Если команда выдала 200 строк — оставьте 5–10
  ключевых, остальное пометьте `[...]` или ссылкой на сырой файл в
  `scripts/output/` (этот каталог в `.gitignore`).
* **Цитируйте дословно.** Не пересказывайте вывод командой, копируйте
  буквально — это материал для аудита.
* **Тайминги.** Если что-то заняло заметное время (build, бенчмарк) —
  пишите длительность.
* **Числа — без округления.** «593.4 Мбит/с», не «полгигабита».
* **Конфигурация модуля.** Если меняли что-то — пишите что именно, чем
  откатывается. Если ничего не меняли — пишите «read-only».
